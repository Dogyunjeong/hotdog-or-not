# Environment

## local environment

- The web app (including `/api`) runs locally with `yarn dev`
- Supabase runs locally in Docker via the Supabase CLI (`yarn db:start`)

## Environment Configuration

### **CRITICAL RULE: API Environment Variables**

- **Types are defined in `shared/types` (`SharedTypes.SeamflowEnvironment`)** — add new vars there first
- **Read env only through `getEnvironmentVariable()` in `server/configs/app.config.ts`** — never `process.env` directly
- Resolve env lazily inside client getters (`getOpenAIClient`, `getSupabaseClient`) so `next build` needs no secrets
- Local: `.env.local` (see `.env.example`). Vercel: project env vars per environment.

```bash
OPENAI_API_KEY=...
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_SERVICE_ROLE_KEY=...
```

# project structure

One Next.js project. Folders keep the old package boundaries:

| Folder                                          | Was                        | Rule                                                                                                               |
| ----------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `shared/`                                       | `shared-*` packages        | Isomorphic. MUST NOT use Node APIs (fs, Buffer, ...) or DOM APIs. Imports only from `shared/`.                     |
| `server/`                                       | `server-*` / `apps/api`    | Server-only. Entry points `import 'server-only'`. MUST NOT be imported by `components/`, `hooks/`, `controllers/`. |
| `app/`, `components/`, `hooks/`, `controllers/` | `front-*` / `frontend/web` | Browser + RSC. Talk to the API only via `shared/controllers`.                                                      |

Imports use the `@/` alias (`@/shared/types`, `@/server/clients/...`), no file extensions.

## `./shared`

- `shared/types` — source of truth for domain types, re-exported as namespaces: `HotdogTypes`, `VisitorSessionTypes`, `SharedTypes`
  - `[domain]/[Domain].type.ts`, `[domain]/[Domain].const.ts`
  - `database/Database.type.ts` is generated by `yarn db:types` — never hand-edit
- `shared/utils` — `FetchRequest`, `uploadFileToSignedUrl`, `ExpectedServerError`, domain validators used by both browser and API
- `shared/controllers` — API controllers, `[domain]/[Domain].controller.ts`

## `./server` (Backend)

Next.js route handlers in `app/api/**/route.ts` are thin adapters: they instantiate a handler and forward the Web `Request`.
GET adapters call `await connection()` first — with Cache Components, Next otherwise tries to prerender the GET and interrupts it with an internal error that the handler's `try/catch` would swallow.
No Next.js imports inside `server/`.

### Architecture

Domain and concern focused. Focus on modularizing.

- `./server/api/[domain]`
  - `[Domain].handler.ts` — `(request: Request) => Promise<Response>`; resolve visitor session, parse input, call services, set cookie, `handleError`
  - `[Domain/Concern].service.ts` — business logic; one service per concern (e.g. `HotdogImageUpload.service.ts`, `HotdogClassification.service.ts`)
  - `[Domain].prompt.ts` — LLM model, instructions, and output schema for that domain
- External systems are reached through clients, not extra service layers:
  - `server/clients/openai/getOpenAIClient.ts` — OpenAI SDK client
  - `server/clients/supabase/getSupabaseClient.ts` — Supabase SDK client (service role); services query tables with it directly
  - `server/clients/supabase/SupabaseStorage.client.ts` — `SupabaseStorageClient` (signed upload URL, info, download, move, signed read URLs) + `STORAGE_BUCKET` ids
  - Extend these clients with generic operations; keep domain rules (paths, validation) in services
- No `*.2nd.service.ts` layering — one service per domain concern, composing clients directly
- Clients are injected into handlers/services (constructor) so tests can pass fakes (see `test/helpers`)
- Throw `ExpectedServerError` for errors the user should see (validation, not found) with a user-friendly message. Anything else becomes a 500 with a generic message and is logged.
- Map DB rows (snake_case) to domain types (camelCase) inside the service.

### Visitor session

- Anonymous visitor identity: `visitor_sessions` row + httpOnly cookie `seamflow_visitor_session` (`server/utils/visitorSessionCookie.ts`)
- Every session-scoped handler: `VisitorSessionService.resolveVisitorSession({ visitorSessionId: readVisitorSessionIdFromRequest(request) })` → do work → `withVisitorSessionCookie(response, visitorSession.id)`
- Visitor-owned storage paths start with `{visitorSessionId}/`; always check ownership server-side

## Frontend (`app/`, `components/`, `hooks/`, `controllers/`)

Next.js 16 App Router. Read `node_modules/next/dist/docs/` before using a Next.js API.

- all frontend code must meet type definitions in `shared/types`
- communicate with the API through `shared/controllers` (instances in `controllers/apiControllers.ts`)
- `components/primitives/` reusable primitives; `components/[Domain]/` domain UI; `hooks/` stateful logic split from UI
- Style with Tailwind using the design tokens in `app/globals.css` (`@theme`) — no hardcoded colors
- Validation shared with the API lives in `shared/utils` so the client gives instant feedback with the same rules

## `./supabase`

- `config.toml` — local Supabase CLI config
- `migrations/` — timestamped SQL migrations. Enable RLS on every table.
- Storage buckets are created in migrations (`insert into storage.buckets ...`), private by default; only the API (service role) accesses them

## `./plans`

Build plans for the project. **always refer to this folder before starting implementation**

## test

- unit test: next to the target file, `*.test.ts`
- API tests: `./test/api-tests/[domain]/` — call the handler through shared controllers by stubbing `fetch`, with fake external clients (see `test/api-tests/hotdog`)
- **IMPORTANT**: Whenever a backend feature is added, corresponding API tests MUST be added
